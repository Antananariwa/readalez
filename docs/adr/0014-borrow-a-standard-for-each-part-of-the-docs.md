# 14. Borrow a published standard for each part of the docs

Date: 2026-11-14
Status: Accepted. Superseded in part by [ADR 0015](0015-keep-the-writing-rules-in-claude-md.md): the live writing rules are in CLAUDE.md, and this ADR is the record of which standards were chosen. Local rule 1 is superseded by [ADR 0016](0016-write-spec-md-as-openfasttrace-items.md).

## Context

Eight issues and PRs between 2026-11-02 and 2026-11-14 reworked the doc rules or the docs written under them, and each fixed one problem (#105 lists them). #105 redesigns the docs and agent instructions so that each rule is borrowed from a published standard, and #109 is its first step: choose a standard for each part.

No single published pattern was found that covers every part (#105). #109 asks for standards that are published with a licence that allows use, used by named projects, and small, with few sources overall, and for anything else to be listed as a local rule with its reason.

The pages below were read on 2026-11-14. Each quoted phrase was then searched for in its page with a script (run while working on #109, not in the repo), and all were found. What was not read is listed under Consequences.

One study on agents was read, [Gloaguen et al. 2026](https://arxiv.org/abs/2602.11988): giving agents context files "does not generally improve task success rates, while increasing inference cost by over 20% on average". Its [full text](https://arxiv.org/html/2602.11988) says developer-written files did better than LLM-generated ones, and that "Human-written context files should only include instructions required for coding agents that are not already present in the README". The pages read for EARS, Kiro, OpenSpec and Spec Kit give no numbers on their effect.

## Decision

Each part of the docs follows the standard in its row. Where the standard has a rule, that is the rule. The last column lists every change Readalez makes to it.

Local rules, which no source read gives:

1. **SPEC.md's shape.** A feature says what it does, then has rule lines, each with its "Why:", then Checks, each labelled with where it runs. Why: the reasons travel with the decisions (ADR 0001), and the requirement formats read have no place for a reason. Neither #99 nor #104 records a problem with SPEC.md's sentence form.
2. **Rules about who may do what live only in CLAUDE.md and `.claude/agents/`.** Why: #42 found such rules inside content docs.
3. **A feature issue holds Goal, Acceptance criteria and Out of scope.** Why: no source read covers a feature request.
4. **A PR also has Verified, Review and How to test.** Why: the owner reviews evidence instead of re-running everything, and the hook and docs/reviews.md read the Review section (#62).

No published rule was found that keeps a concept's name apart from its label on the screen (#104). The Names row gets there by combining two rules: the glossary names the concept, and the style guide says to write about the feature rather than the UI element.

## Consequences

- Steps 2 to 7 of #105 follow the table and link this ADR instead of restating it. A step that finds a standard doesn't fit a case proposes a new ADR that supersedes this one.
- SPEC.md gains a glossary (#106). CLAUDE.md's Writing docs section can point here for its sources (#110).
- The table draws on thirteen sources. That is more seams than one template would have. arc42 as a whole would be one source, but it has 12 sections and ARCHITECTURE.md is 28 lines.
- Looked at and not chosen:
  - [Diátaxis](https://diataxis.fr/): its [colophon](https://diataxis.fr/colophon/) says "The original context for the Diátaxis approach was limited to software product documentation", and Readalez's only user doc is the README.
  - [EARS](https://alistairmavin.com/ears/): five sentence patterns, used by [Kiro's requirements files](https://kiro.dev/docs/specs/feature-specs/). Its page states no licence ("All Rights Reserved"), the patterns have no place for a reason, and all 14 features would be rewritten in "shall" sentences.
  - [OpenSpec](https://github.com/Fission-AI/OpenSpec), [Spec Kit](https://github.com/github/spec-kit) and Kiro: each brings its own file set and workflow.
  - [MADR](https://adr.github.io/madr/): adds Considered Options and "Chosen option: …, because …", and an optional decision-makers field, which records what #99 removes. New ADRs would differ in format from the 13 accepted ones.
  - [req42](https://docs.req42.de/category_a/): 12 sections, of which section 4 is the product backlog. No named users were found on its pages, and its tips were not read.
  - [Volere](https://www.volere.org/templates/volere-requirements-specification-template/): its page gives each requirement a Fit Criterion, "a measurement against which it can be tested", as SPEC.md's Checks do, but the template has a usage fee. Whether its requirement shell has a field for the reason is not checked: the page shows the shell as a picture.
  - Conventional Commits, The Good Docs Project's Terminology system (11 columns) and Standard Readme: more structure than this repo uses.
- Not read: OpenAI's harness-engineering post and ISO 24495-1 (both returned HTTP 403); the EARS paper; Volere's template; The Good Docs Project's guides; MADR's templates as tagged for 4.0.0 (the `develop` branch was read); Diátaxis's tutorial and how-to pages; Google's developer style guide beyond UI elements and the start of its word list; 26 of the 30 agent files #105 sampled.
- Read in part: the fetch tool cut long pages near 40,000 characters, which affected Linux's submitting-patches page, Claude Code's memory page, Wikipedia's Verifiability page and the arXiv paper's full text. ICD 203 was read as text pulled from its PDF by a script; standard 4 did not come out readable. The fetch tool got the PDF after two redirects; during review, `curl` got HTTP 403 from both addresses, and the reviewer confirmed the quote in a Wayback Machine copy.
- Revisit if a published pattern appears that covers every part, or if a study shows that a requirement format changes how well agents build from a spec.
